Why Freight

One workflow for native packages

Freight keeps source packages, dependency fetching, build metadata, documentation, and editor tooling tied to one project manifest.

01

Project-local deps

Registry, Git, URL, system, and path dependencies resolve into a local .pkgs/ cache.

02

Native build graph

C, C++, Fortran, assembly, and mixed-language targets build through one DAG-aware pipeline.

03

Editor metadata

freight lsp generates compile commands for clangd and provides manifest diagnostics.

04

Release outputs

Install to a prefix, stage with DESTDIR, package archives, and publish to a registry.

Example manifest

Describe targets and dependencies in freight.toml

A single manifest declares package metadata, public headers, executable targets, compiler settings, features, and platform-specific dependencies.

Read the manifest reference 
[package]
name = "hello"
version = "0.1.0"
license = "MIT"

[lib]
name = "hello"
srcs = ["src/hello.cpp"]
hdrs = ["include/hello/hello.h"]

[[bin]]
name = "hello"
src = "src/main.cpp"

[language.cpp]
std = "c++20"

[dependencies]
fmt = "10"
mathlib = { path = "../mathlib" }

[os.windows.dependencies]
winapi = "0.3"

Common workflows

Commands that match the project lifecycle

Build loop

freight check
freight fetch
freight build --time-passes
freight test
freight run -- --help

Dependencies

freight add fmt@10
freight add mathlib --path ../mathlib
freight fetch
freight tree
freight outdated

Release

freight build --release
freight install --prefix /usr/local --destdir target/stage
freight package --target x86_64-linux-gnu
freight publish
